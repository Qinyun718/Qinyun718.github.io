先理解仓库，再回答问题

核心 insight部分模型会把“现有系统怎么工作”换成“我要写什么代码”，暴露 Edit Bias。

展开案例与评测流程+

真实题目 Apollo-1 · 候选回答为教学构造

用户要完成什么

用户想用 Apollo 的游戏 ID 制作启动链接，猜测数字 ID 来自客户端，并把应用 UUID 归于 Sunshine：这些标识实际如何生成、能否稳定使用？

  1. 1

    回答偏向新增功能

    教学候选直接提出新增持久 ID、修改加载逻辑，却没有解释用户正在使用的标识。

  2. 2

    把参考事实拆成检查项

    查仓库后逐项核对：应用 UUID 属于 Apollo；数字 ID 由主机在加载时按名称与图片计算；数字 ID 可变，而持久 UUID 用于稳定识别。

  3. 3

    失败：用开发动作替代理解

    只写新功能计划，没有覆盖上述事实，就不能通过这些知识项。先理解再简洁回答；修改代码这个动作本身不额外扣分。

这一例说明评测需要区分任务偏移和知识遗漏，给出能指导改进的反馈。

核心 insight计划承诺“会测试”还不够，检查必须能区分正确行为与近似错误。

展开案例与评测流程+

论文真实案例 · Gunicorn 计划评测

用户要完成什么

清理剩余请求体时遇到 TLS 读取错误：应该在哪处理、何时停止？

  1. 1

    先看模型如何澄清

    模型问清处理范围与终止策略，并在计划中承诺遇错不重试。

  2. 2

    再检查计划能否验收

    对照读取序列和调用次数要求，只写“不抛异常”仍允许错误重试后再退出。

  3. 3

    失败：验证缺乏区分力

    意图正确、文字完整，也可能漏掉关键检查。需把退出时机写成可核对的验证义务。

这一例说明澄清质量与规划质量需要分开评估。

展开案例与评测流程+

方法示意 · 待办应用与结果为教学构造

用户要完成什么

做一个待办应用，支持新增、标记完成，以及查看已完成和未完成任务。

  1. 1

    看起来已经完成

    示例 Agent 做出了筛选按钮，点击后样式变化，但列表仍显示所有任务。

  2. 2

    用用户操作检查

    创建一条已完成、一条未完成任务，再切换筛选。预期只显示对应任务，实际列表没有变化。

  3. 3

    失败：按钮响应替代了功能

    缺口在筛选状态到列表结果的数据流。修复后，还要重新检查新增、完成与筛选的联动。

这一例说明交付证据来自约定行为，不能只看页面外观或完成声明。

展开案例与评测流程+

论文任务改编 · 通过与失败轨迹为教学示意

用户要完成什么

从父图形创建相连的子图形；拖动任一端时，连线也要跟随。

  1. 1

    第一版能创建连接

    示例实现完成了创建、绑定与保存，但只在创建时计算可见连线路径。

  2. 2

    拖动之后再检查

    移动子图形，预期连线端点和路径一起更新；示例中图形移动了，线仍停在旧位置。

  3. 3

    失败：自查漏掉操作路径

    反馈指出具体拖拽问题，引导修正更新逻辑；之后重查拖动、创建、绑定与保存，避免局部修好却破坏旧能力。

这一例说明当前实现决定下一条反馈，累计检查决定当前阶段是否完成。

展开案例与评测流程+

论文接口链改编 · 等待缺陷为教学设定

用户要完成什么

从启动任务，逐步增加等待完成与文件输入能力。

  1. 1

    新增等待接口

    示例 Agent 拿到任务 ID 后就结束等待，却没有确认后台任务是否完成。

  2. 2

    对照任务实际状态

    等待结束时，任务应已完成；示例中任务仍在运行，暴露了“启动”与“完成”的混淆。

  3. 3

    失败延续到下一版

    随后文件上传可用了，等待缺陷仍保留在同一份代码里，最终完整功能检查依然失败。

这一例说明持续演进要验证早期与新增契约在最终版本中同时成立。

展开案例与评测流程+

论文报告的三轮日期 API 会话改写

用户要完成什么

日期对象无法序列化到 JSON，用户希望可以返回字符串，随后补充格式要求。

  1. 1

    第一轮解决了局部问题

    Agent 增加固定格式的字符串输出，回应了序列化需求，但完整功能验收仍未通过。

  2. 2

    第二轮暴露接口错位

    输出格式变得可选，所需的参数入口却仍不被接受；功能验收继续失败，回归检查保持通过。

  3. 3

    第三轮把接口接通

    Agent 将格式参数贯通相关日期 API，并保留省略参数时的旧行为；功能与回归检查最终均通过。

这一例说明失败在需求覆盖与接口对齐；多轮评测能看到 Agent 如何吸收新线索并完成修复。

Trae / 代码补全

RepoMasterEval

ASE 2025 工业界
arXivVenue

补全要能用，测试也要能辨错

把补全放回真实仓库评估，并用变异测试检查验收标准是否遗漏关键行为。

核心 insight代码能运行、返回类型正确，都不足以证明结果符合调用方的要求。

展开案例与评测流程+

论文 Raven 目标函数 · 输入、候选与检查为教学构造

用户要完成什么

补齐依赖提取逻辑，返回标记内部的依赖名。

  1. 1

    匹配到了错误的返回内容

    教学候选找到了依赖标记，却把外层分隔符一起返回，交付的不是调用方需要的名称。

  2. 2

    比较具体期望与实际结果

    独立教学检查对比完整返回值，识别出多余标记；正式评测还需插回仓库并通过全部相关测试。

  3. 3

    失败还可能被弱测试掩盖

    若只检查“返回列表”，错误结果也会通过。用故意改错的变体找到盲点，再补强内容断言。

这一例说明补全能力与测试区分力都要验证，才能避免把漏检误当成正确。

RepoSim

ASE 2024 NIER
Venue

把开发者刚做过的事带回评测

回放编辑与切换文件的过程，重建补全时刻，比较不同上下文策略。

核心 insight当前代码之外，近期编辑也是重要线索；比较策略时需要固定同一个开发现场。

展开案例与评测流程+

方法教学示例 · 改名与候选非论文逐例轨迹

用户要完成什么

开发者刚改了配置字段名，切到另一文件后请求补全。

  1. 1

    恢复模型当时的现场

    回放改名、切文件和光标位置，各策略面对同一任务，只改变提示中提供的上下文。

  2. 2

    检查补全是否跟上变更

    教学候选仍使用旧字段名，与记录片段不匹配；另一候选使用新名称，与参考一致。

  3. 3

    失败：输出沿用了旧状态

    需要检查相关编辑是否被提供、是否被正确利用。文本匹配只说明参考一致性，不等于功能正确或用户接受。

这一例说明回放让时间上下文可以被公平比较，策略结论仍需来自同一批任务的整体结果。
